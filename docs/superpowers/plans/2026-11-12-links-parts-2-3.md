## Rulings that bind every slice

1. **Self-links are plain text.** A name whose home is the view already showing does nothing when clicked, so it is body text: ORD in the rows of ORD's Schedule board, the type cell of a Fleet table already filtered to that type, a hub page's own code, a fleet page's own type. (The brief-chip precedent, DESIGN.md 2026-11-10.) The other end of a route, when it is a different hub, links.
2. **A follow that stays on the same tab resets nothing.** The "reset, then apply, then scroll" behaviour is for arriving from another tab. A type clicked inside the Fleet table sets the type filter and leaves search, Wi-Fi and status alone; a hub clicked inside Schedule changes the board's hub and keeps the reader's direction, day and filters. No history entry, no focus move.
3. **Secondary names in a touch row that is already one tap target are inert links**, exactly as part 1's `finePointerOnly`: an `<a>` that takes no taps and shows no underline on a coarse pointer, live with a mouse. The phone Schedule tail is one of these and loses its dotted underline. Never an allowlist entry to get the audit to zero.
4. **Express numbers are not widened.** `unitedNumber` (operating code → United number) applies only where part 1 put it: Starlink-feed rows marked United and the inbound label. Elsewhere a row links its flight number only when it carries a United number (`flightIATA`, a `UA…` ident); a bare operating callsign (`SKW5575` in the Live sidebar or the ticker) stays plain.
5. **Type links go by tail** (`fleetTypeCodeForTail`) when the row has one; otherwise only an exact fleet-database type string links. ICAO codes (`B739`, `B772`) and clipped provider text never decide a link on their own.
6. **Express tails:** before linking Express tails wholesale, open the aircraft dialog for at least five of them (different operators) and confirm it has content; if it is thin for a class of tail, leave that class plain and report it.
7. **A count, tile, bar or chip that summarizes rows** is a `<button>` that sets the filter of the list it summarizes when that filter exists; where the filter is local state with no control, the tile stays text. Tiles inside a `role="status"` live region stay text.
8. **Ticker lines and map legend rows stay plain** (spec).
9. **Dirty-state equivalence.** Every new in-place destination gets a test that starts from a dirty state of the destination (filters set, another direction or sub-view showing) and ends where a cold load of the same address does. This class was missed twice in part 1.
10. **Provider budget.** Do not run anything in a loop against production APIs. Slices test with vitest and, for a browser look, `bunx astro dev`/`preview` once. The proxied `ui-audit` runs once per pull request, at integration. Never script requests to `/api/schedule` or `/api/flight`.
11. **Records and guard lists are written at integration only** (see the ownership table). Slices leave `DESIGN.md`, `CHANGELOG.md`, `package.json`, `tests/design-guards.test.js` and `scripts/ui-audit.mjs` alone and list in their report what the records should say and which files the guards should now cover.

## 2-foundation: carry-overs from part 1 and shared additions

- After Back (popstate/hashchange) that changes the tab: announce the tab and move focus to its panel, reusing the follow path's helpers.
- `pushHistoryEntry` wrapped so a browser that refuses a history call still gets `setTab`.
- A follow made before the Fleet database has loaded must not strip a cold load's own `?type=`/`?filter=`/`?view=` before the Fleet view has read them.
- A Fleet link held for the database gets the same deadline as the cold path.
- `announce()` re-announces a sentence equal to the previous one.
- The tab panel that receives focus shows a focus ring for keyboard focus only.
- The inbound label reads an Express prefix as United's only from the feed's `flightIATA`, not from a callsign fallback (`starlink-utils.js`, part 1's `starlinkInboundLabel`).
- Same-tab follows (ruling 2): `follow` distinguishes "arriving" from "already here"; the Fleet link carries which it is.
- A followed hub link that ARRIVES at Schedule from another tab resets Schedule's status, type and search filters (a `scheduleLink` sequence in `ui.tsx`, consumed by `ScheduleView` in slice 2a); staying on Schedule resets nothing.
- `hub-link.js`: `hubStatusLink(code, 'weather' | 'nas')` → `/?tab=weather&hub=EWR`, `/?tab=weather&section=nas`; `EntityLinks.tsx`: `HubStatusLink`.
- `fleet-type-link.js`: `fleetTypeCodeFor({ reg, typeText, fleetByReg })` → by tail, else an exact fleet type string, else null.
- `link-guard.js`: `findUnlinkedNames` takes `self` (the view's own hub and type) so ruling 1's plain names are not violations.
- The part 1 test gaps: BriefChip's null-tab branch; pass-through tests assert state unchanged; the `defaultPrevented` return.

## Part 3 specifics

- Runtime-filled tables (hub board, FleetLive, flight page) link through the bundled client scripts; `bun run build` must still pass `scripts/verify-csp-hashes.mjs`. No inline script, no `on*=` attributes.
- Registry tails use the existing `touchRowLink` pattern; a 188-row table must not grow taller with a mouse.
- The hub "Key Routes" transform links hub codes only, skips the page's own hub, and never touches text already inside an anchor.
- `/hubs/gum` and `/hubs/nrt` get their live-map link back; confirm in built HTML.
- `StatTile` / `StatStrip` take an optional `href`; a tile links only when the destination lists what it counts.
- "Starlink Tracker" on `/fleet` opens the Starlink tab.
- The guard for static pages is a vitest test over built HTML (tests that read `dist/` already exist and skip when it is absent); the runtime-filled tables are guarded by unit tests of their row builders.
